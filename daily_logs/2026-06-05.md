# 📝 [TIL] 2026-06-05 | 가상 오도메트리 실패 분석 및 RF2O 센서 우회 SLAM 개통

## 1. 개요 및 하드웨어 구성

- **목표:** ESP32 기반의 모바일 로봇 구동계와 ESP32-S3 기반의 LDS14 라이다 센서를 무선(Wi-Fi UDP)으로 ROS2 환경과 연동하여 2D SLAM(`slam_toolbox`) 구현.
- **하드웨어 제약:** 로봇의 좌측 바퀴 엔코더 핀 물리 파손. 우측 물리 틱 데이터만 정상 수집 가능.
- **기존 임시 대책:** 정상 작동하는 우측 엔코더 데이터와 아커만 조향 기하학 모델을 기반으로 좌측 바퀴의 거리를 수학적으로 가상 예측하는 '순수 가상 오도메트리 엔진' 구축.

## 2. 발생한 문제점 및 원인 분석 (Troubleshooting)

### 🔴 문제 1: 코드 수정이 반영되지 않고 지도가 아예 안 그려짐

- **원인:** 파이썬 노드 수정 후 `colcon build` 누락. `-symlink-install` 옵션 없이 초기 빌드가 진행되어 시스템이 `src/` 폴더의 수정본이 아닌 `install/` 폴더에 복사된 **과거의 낡은 파이썬 파일**만 계속 실행함.
- **해결:** 기존 빌드 내역(`build/`, `install/`)을 완전히 삭제한 후 `colcon build --symlink-install` 옵션으로 재빌드하여 실시간 코드 반영 인프라 구축.

### 🔴 문제 2: 라이다 데이터 수신 끊김 및 패킷 유실 (`0개` 수신)

- **원인:** Windows 방화벽 규칙 제한 및 WSL2(가상 머신)의 가상 IP 분리로 인해 외부 ESP32-S3가 쏘는 UDP 패킷(`12346` 포트)이 리눅스 커널 내부로 들어오지 못함.
- **해결:** 1. Windows 파워쉘에서 `New-NetFirewallRule`로 해당 UDP 포트 방화벽 강제 개방.
2. `.wslconfig` 설정 파일에 `networkingMode=mirrored` 모드를 적용하여 Windows와 WSL2의 네트워크 인터페이스를 일치화시킴으로써 `nc -lu 12346` 생(Raw) 패킷 수신 성공.

### 🔴 문제 3: 로봇의 위치 순간이동(Warp) 및 1초 주기 맵 깜빡임 현상

- **원인:** 가상 오도메트리의 누적 오차 및 데이터 뻥튀기 현상과 `slam_toolbox` 시간 동기화 메커니즘의 충돌.
    1. 무선망 지연으로 인해 라이다 타임스탬프와 오도메트리 타임스탬프가 미세하게 어긋나 슬램 엔진이 데이터를 대량 드랍함 (`Message Filter dropping message... queue is full`).
    2. 이를 해결하고자 가만히 있어도 1초마다 지도를 강제 갱신(`map_update_interval: 1.0`)하게 유도하자, **[라이다 눈이 본 진짜 지도]** 위에 [튀어버린 오도메트리 축 기준의 유령 지도]가 1초마다 번갈아 겹쳐 그려지며 화면이 격렬하게 깜빡이고 로봇이 점프함.

## 3. 최종 해결 및 우회 아키텍처 (RF2O 도입 결정)

- **소프트웨어적 센서 대안 도입:** 물리적으로 고장 나 신뢰성이 제로에 가까운 바퀴 엔코더를 완전히 배제하기로 결정. 대신 라이다 센서의 점군 데이터 연속 변위를 미분하여 역으로 로봇의 선속도와 각속도를 계산하는 **`rf2o_laser_odometry` (Laser-based Odometry)** 패키지 전격 도입.
- **기대 효과:** 라이다와 오도메트리가 동일한 시간 축(라이다 데이터 클럭)에서 동기화되므로 시간 축 왜곡 현상이 근본적으로 차단되며, 바퀴의 미끄러짐이나 엔코더 결함에 영향을 받지 않는 무결점 가상 좌표계 변환 실현.
