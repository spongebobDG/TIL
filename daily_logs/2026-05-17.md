### 🎯 Issue: 로봇과 라이다 맵이 영구적으로 엇나가는 현상 (스윙 현상)

원인: nav2_params.yaml의 Costmap 설정에 robot_radius: 0.20이 설정되어 있어, 실제 가로 13cm/세로 19cm인 로봇을 지름 40cm의 거대한 원형 로봇으로 인식함. 충돌 방지 시스템이 길을 막은 것으로 판단.

해결: robot_radius를 삭제하고, 실제 로봇 크기에 안전 여유분(5mm)을 더한 직사각형 footprint: [ [0.10, 0.07], [0.10, -0.07], [-0.10, -0.07], [-0.10, 0.07] ]를 Local 및 Global Costmap에 모두 적용.

### 🎯 Issue: 좁은 복도나 장애물 근처에서 로봇이 멈추는 현상

* **상황 및 증상:** 
  - Global Path(초록색 선)가 생성되지만, 로봇이 전진하지 못하고 제자리에서 버벅거리며 주행을 포기함.

* **근본 원인 (Root Cause):**

  - 로봇의 물리적 크기와 인지 시스템의 차이점을 고려하여, Costmap 설정을 적절히 조정하는 것이 중요하다는 점을 배웠음.

**[내 기록]**: Phase 3: ROS2 빌드 시스템 및 파라미터 타입 에러
Issue 3: YAML 파라미터 수정 사항 미반영 및 FATAL 에러 다운

증상: 1. 코드를 수정해도 이전 설정값으로 계속 동작함.
2. [global_costmap] 노드가 타입 에러를 뿜으며 자율주행 노드 전체가 셧다운됨.

원인: 1. 기본 colcon build 사용으로 인해 src의 수정본이 install 폴더로 실시간 갱신되지 않음.
2. cost_scaling_factor 값에 정수형(30)을 입력하여 C++ 런타임에서 Type mismatch 발생. (ROS2는 엄격한 double 타입을 요구함)

해결: 1. rm -rf build/ install/ 후 colcon build --symlink-install 명령어로 심볼릭 링크 빌드를 적용하여 실시간 파일 동기화 환경 구축.
2. 파라미터 값을 실수형(30.0)으로 수정하여 FATAL 에러 해결.

### 🎯 Issue: ROS2 빌드 시스템 및 파라미터 타입 에러

* **상황 및 증상:** 사용자가 코드를 수정하고도 이전 설정값으로 계속 동작하며, [global_costmap] 노드가 타입 에러로 인해 자율주행 노드 전체가 셧다운되는 문제 발생.

* **근본 원인 (Root Cause):**
  - 기본 `colcon build` 사용으로 인해 `src`의 수정본이 `install` 폴더로 실시간 갱신되지 않음.
  - `cost_scaling_factor` 값에 정수형(30)을 입력하여 C++ 런타임에서 타입 불일치(Types mismatch) 발생. ROS2는 엄격한 double 타입을 요구함.

* **해결 방안 및 배운 점:**
  - `rm -rf build/ install/` 명령어를 사용하여 기존 빌드 폴더를 삭제하고, `colcon build --symlink-install` 명령어로 심볼릭 링크 빌드를 적용하여 실시간 파일 동기화 환경 구축.
  - 파라미터 값을 실수형(30.0)으로 수정하여 FATAL 에러 해결.
  - 이러한 문제는 ROS2의 타입 강화와 실시간 갱신에 대한 이해가 필요함.

* **Keywords:** #ROS2 #C++ #타입불일치 #실시간파일동기화 #파라미터수정

**[내 기록]**: Phase 4: 라즈베리파이(Edge Device) 성능 병목 최적화 (The Final Boss)
Issue 4: AMCL 프레임(map) 생성 실패 및 TF Extrapolation Error (시공간 붕괴)

증상: tf2_echo map base_link 시 map 프레임이 존재하지 않는다는 에러 발생 및 AMCL이 라이다 메시지를 너무 오래된 데이터(Timestamp 지연)라고 판단하여 지속적으로 Drop 함.

원인: 라즈베리파이 4B의 CPU 연산량 한계로 인해 EKF와 AMCL 연산이 지연됨. 이로 인해 센서 데이터(LiDAR)의 타임스탬프와 로봇 뼈대(TF)의 갱신 주기 사이에 심각한 오차(Latency)가 발생하여 데이터가 폐기됨.

해결 (CPU 부하 완화 및 지연 허용치 증가):

EKF frequency를 10.0 Hz로 하향 조정하여 연산 템포 안정화.

amcl 노드의 max_particles를 2000에서 1000으로 줄여 CPU 부하 감소.

Costmap 설정에 transform_tolerance: 1.5를 부여하여 라즈베리파이의 연산 지연(TF 딜레이)을 소프트웨어적으로 너그럽게 허용.

amcl에서 set_initial_pose: True를 활성화하여 맵 초기화 강제 수행.

### 🎯 Issue: AMCL 프레임(map) 생성 실패 및 TF Extrapolation Error

* **상황 및 증상:** 라즈베리파이(Edge Device)에서 AMCL 노드가 라이다 메시지를 오래된 데이터로 판단하여 지속적으로 Drop하고 있으며, tf2_echo 명령어를 사용해 map frame에 대해 base_link를 요청할 때 map 프레임이 존재하지 않는다는 에러가 발생합니다.

* **근본 원인 (Root Cause):** 라즈베리파이 4B의 CPU 연산량 한계로 인해 EKF(Estimation Kalman Filter)와 AMCL(Autonomous Mobile Robot Localization) 연산이 지연되며, 이로 인해 센서 데이터(LiDAR)의 타임스탬프와 로봇 뼈대(TF)의 갱신 주기 사이에 심각한 오차(Latency)가 발생하여 데이터가 폐기됩니다.

* **해결 방안 및 배운 점:** 
  - EKF frequency를 10.0 Hz로 하향 조정하여 연산 템포를 안정화하고 CPU 부하를 감소시킵니다.
  - amcl 노드의 max_particles를 2000에서 1000으로 줄여 CPU 부하를 더욱 감소시킵니다.
  - Costmap 설정에 transform_tolerance: 1.5를 부여하여 라즈베리파이의 연산 지연(TF 딜레이)을 소프트웨어적으로 너그럽게 허용합니다.
  - amcl에서 set_initial_pose: True를 활성화하여 맵 초기화 강제 수행으로 인해 AMCL 노드가 정상적인 위치 추정에 도움이 될 수 있습니다.
