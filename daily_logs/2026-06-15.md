### 🎯 Issue 1: 웹 대시보드에서 차량 상태가 항상 "0 online"으로 표시됨

* **상황 및 증상:**
  - WebSocket으로 `fleet_status` 메시지는 정상 수신 (17~31개/10초)
  - 하지만 브라우저 화면에서 차량이 전혀 ONLINE으로 표시되지 않음

* **근본 원인 (Root Cause):**
  - `dashboard_server.py`의 `_broadcast()` 함수에서 `_clients -= dead` (augmented assignment)가 Python 스코핑 규칙에 의해 `_clients`를 **지역 변수로 취급**하게 만들어 `UnboundLocalError` 발생
  - 이 예외가 `asyncio.run_coroutine_threadsafe()`의 Future 래퍼에 의해 **silently swallowed** 되어 디버깅이 어려웠음
  - 증상: `_broadcast()` 호출마다 크래시 → WebSocket 전송 0건

* **해결 방안 및 배운 점:**
  - `_clients -= dead` → `_clients.difference_update(dead)` 변경 (in-place 메서드는 새 binding을 만들지 않아 UnboundLocalError 없음)
  - `asyncio.run_coroutine_threadsafe` → `call_soon_threadsafe(_main_loop.create_task, ...)` 로 교체하여 예외가 실제로 노출되도록 수정
  - **핵심 교훈**: Python에서 `x -= y` 형태는 함수 내 어디서든 `x`를 지역변수로 만들어버림. 전역 set을 in-place로 수정할 때는 `.difference_update()`, `.add()`, `.discard()` 같은 메서드를 사용해야 함

* **Keywords:** #Python #asyncio #UnboundLocalError #WebSocket #FastAPI #ROS2

### 🎯 Issue 2: ROS2 타이머가 시뮬에서 한 번도 발화하지 않음

* **상황 및 증상:**
  - `dashboard_server.py`에 `create_timer(0.2, _cb_tf_poses)` 설정했는데 타이머 콜백이 단 한 번도 실행되지 않음
  - `/tmp/tf_debug.txt` 파일이 아예 생성되지 않는 것으로 확인

* **근본 원인 (Root Cause):**
  - `central.launch.py`에서 dashboard 노드에 `use_sim_time: True` 설정
  - 시뮬(`sim` tmux 세션)의 `/clock` 토픽이 중앙(`central` tmux 세션)으로 **전달되지 않음**
  - ROS2에서 `use_sim_time: True`인 노드는 `/clock` 메시지가 없으면 시간이 0에 멈춰 타이머가 영구히 발화하지 않음

* **해결 방안 및 배운 점:**
  - `central.launch.py`에서 `use_sim_time: True` → `use_sim_time: False`로 변경
  - **핵심 교훈**: WSL2에서 tmux 세션을 나눠 실행할 때 VOLATILE QoS 토픽 (`/clock`, `/tf`)은 DDS 세션 경계를 넘지 않음. 대시보드처럼 별도 세션에서 도는 노드는 실시간 벽시계(wall clock)로 실행해야 함

* **Keywords:** #ROS2 #SimTime #FastDDS #DDS #tmux #WallClock

### 🎯 Issue 3: 차량 위치 (peer_2, peer_3)가 대시보드에 표시되지 않음

* **상황 및 증상:**
  - peer_1은 위치 마커가 표시되는데 peer_2, peer_3은 전혀 표시 안 됨
  - TF lookup 오류: `"map" passed to lookupTransform argument target_frame does not exist`

* **근본 원인 (Root Cause):**
  - 대시보드(central 세션)가 TF 버퍼에서 `map → peer_N/base_link` 변환을 조회하려 함
  - `/tf` 토픽은 VOLATILE QoS + 고빈도 발행 → DDS 세션 경계를 넘지 않음
  - 결과적으로 central 세션의 TF 버퍼에는 `map` 프레임 자체가 존재하지 않음

* **해결 방안:**
  - `sim_pose_relay_node.py` 신규 생성: 시뮬 세션 **내부**에서 TF를 조회한 뒤 `/fleet/peer_poses` (RELIABLE + TRANSIENT_LOCAL QoS)로 `PeerPoseArray` 발행
  - TRANSIENT_LOCAL QoS 토픽은 DDS 세션 경계를 넘어 전달됨
  - 대시보드의 `_cb_poses()` 콜백이 이를 수신 → `_fleet_poses_active = True` → TF fallback 자동 비활성화

* **배운 점:**
  - **DDS QoS와 세션 경계**: VOLATILE은 세션 내에서만, TRANSIENT_LOCAL(latched)은 세션 간 교차 가능
  - `/tf`는 VOLATILE이라 세션 경계를 넘을 수 없음. 대신 고수준 집계 토픽(`/fleet/peer_poses`)을 TRANSIENT_LOCAL로 발행하는 릴레이 노드 패턴이 해법
  - `/clock`, `/tf`, 고빈도 LaserScan 등은 세션 분리 시 항상 전달 여부를 확인해야 함

* **Keywords:** #ROS2 #FastDDS #QoS #TRANSIENT_LOCAL #VOLATILE #TF2 #DDS세션경계

### 📚 학습 정리: ROS2 다중 로봇 시스템에서 실차 연결 방법

* **핵심 개념:**
  - 웹 대시보드는 ROS2 토픽만 구독함 → 실차도 같은 ROS_DOMAIN_ID에서 같은 토픽을 발행하면 바로 연결됨
  - `ROS_DOMAIN_ID=42`, `RMW=rmw_fastrtps_cpp`, FastDDS Discovery Server (`192.168.50.10:11811`)
  - 각 차량이 `/{ns}/heartbeat` (FleetHeartbeat) + `/{ns}/amcl_pose` 만 발행하면 대시보드에 ONLINE + 위치 표시

* **실차 연결 체크리스트:**
  ```
  ✅ 같은 Wi-Fi (192.168.50.0/24)
  ✅ ROS_DOMAIN_ID=42 동일
  ✅ FASTRTPS_DEFAULT_PROFILES_FILE 설정 (Discovery Server 연결)
  ✅ /{ns}/heartbeat 발행 (2Hz 이상)
  ✅ /{ns}/amcl_pose 발행 (SLAM 결과)
  ```

* **시뮬 vs 실차 차이점:**
  - 시뮬: `sim_pose_relay_node`가 TF → `/fleet/peer_poses` 변환
  - 실차: coordinator_node가 각 차량 AMCL pose → `/fleet/peer_poses` 집계
