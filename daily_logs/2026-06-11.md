## ROS2 daemon 문제

`ros2 topic list`가 무한 대기하거나 timeout 되는 문제가 있었다.

해결:

```

```

또는 `.bashrc`에 추가:

```
export ROS_NO_DAEMON=1
```

하지만 일부 명령은 `--no-daemon` 위치나 지원 여부가 다를 수 있었다.

## 라이다 딜레이와 QoS

라이다는 최신 데이터가 중요하므로 Best Effort QoS를 사용했다.

```
BEST_EFFORT = 오래된 데이터는 버려도 최신 데이터를 빠르게 봄
RELIABLE = 모든 데이터를 확실히 받음
```

RViz에서는 `/scan_fast`를 사용한다.

```
/scan_fast = Best Effort, RViz 빠른 표시용
/scan = RF2O/SLAM용
```

## Ackermann 조향 문제

Ackermann 차량은 제자리 회전이 불가능하다.

텔레옵 키:

```
j / l  : 정지 상태에서 서보만 좌우 조향
i      : 전진
,      : 후진
u / o  : 전진 + 조향
m / .  : 후진 + 조향
```

처음에는 `j/l`을 누르면 RViz에서 로봇이 제자리 회전한다고 계산되어 지도에 별 모양이 생겼다.

원인:

```
실제 로봇은 제자리 회전하지 않았는데
cmd_vel_odom이 angular.z만 보고 로봇이 회전했다고 계산함
```

해결:

```
linear.x가 거의 0이면 odom yaw를 회전시키지 않도록 수정
```

결과:

```
j/l로 서보만 움직여도 RViz 지도는 더 이상 회전하지 않음
```

## 모터 문제

낮은 속도에서 JGB37 모터가 돌지 않았다.

원인 추정:

```
JGB37 정지 마찰
L298N 전압 손실
좌우 모터 편차
낮은 PWM
```

해결:

ROS2 브리지에 최소 구동 속도를 추가했다.

```
min_drive_linear_mps: 0.20
```

즉 낮은 전진 명령이 들어와도 실제 ESP32에는 최소 0.20 정도로 보낸다.

예:

```
입력: linear.x = 0.12
ESP32 전송: linear = 0.20
```

로그:

```
UDP cmd linear=0.200 steering=0.000
```

## 임시 odom을 쓰는 이유

현재 엔코더가 고장났고 RF2O가 아직 안정적으로 동작하지 않아서 `cmd_vel_odom`을 사용했다.

임시 odom:

```
우리가 보낸 명령을 보고 로봇이 움직였다고 추정
```

한계:

```
바퀴 미끄러짐
모터 편차
배터리 전압 변화
장애물 걸림
```

등을 알 수 없다.

완성형 odom 후보:

```
1. 엔코더 odom
2. RF2O 라이다 odom
3. IMU + encoder/lidar sensor fusion
```

최종 목표는:

```
encoder odom + IMU + lidar SLAM/Nav2
```

현재는 초기 개발을 위해 `cmd_vel_odom`으로 `/odom`과 `/map` 흐름을 먼저 연결했다.

## RF2O 시도

RF2O는 라이다 스캔 변화로 로봇 이동량을 추정하는 도구다.

쉽게 말하면:

```
첫 번째 라이다 그림과 두 번째 라이다 그림을 비교해서
로봇이 얼마나 움직였는지 계산
```

현재 RF2O는 `/scan`을 구독하지만 `/odom`을 만들지 못하고 있다.

로그:

```
Waiting for laser_scans....
```

확인한 것:

```
/scan은 정상 출력
QoS도 BEST_EFFORT로 맞춤
angle_min도 -pi ~ +pi로 변경
```
